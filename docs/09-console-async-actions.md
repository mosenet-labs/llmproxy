# Provider 异步操作与一次性通知

当前控制台已迁移到 `/ui`，包括静态资源和原生 runtime 接口；下文的异步交互约定继续有效。启动与路径见[统一服务](11-unified-service.md)。

关联：[原始需求](00-original-requirements.md)、[控制台设计](07-provider-console.md)、[实施任务](02-tasks.md)。

## 已确认的问题与方案

旧实现使用普通表单 POST，成功后 303 跳转到 `/?notice=enable&provider_name=deepseek`。列表页每次初始化都会把这些参数转换为通知，刷新或再次打开同一链接便重复显示。URL 参数并非 Topcoat 的提交要求。

用户确认改为：**异步提交 → 服务端返回结果 → 局部更新列表 → 显示本次操作通知**。操作不重新导航页面，不使用 URL 或 Cookie 传递通知。先落地本文与任务，再实施。

## 实现方案

- 使用 Topcoat 原生 `#[procedure]` 接收保存和列表操作，继续在服务端执行 CSRF、版本及业务校验。ID 和版本以字符串跨浏览器边界，避免 JavaScript 数字精度损失。
- 业务成功/失败作为返回值传回浏览器，通知包含服务端确认的 Provider 名称。请求失败不得显示成功，不自动重试写操作。
- 使用 `Signal` 控制提交中、通知和编辑状态；使用原生 shard 局部更新 Provider 区域。侧栏、页面 URL、搜索条件和滚动位置保持，变化后的记录按当前筛选重新展示。
- 新建/编辑成功关闭弹窗；失败保留非敏感输入，清空 API Key，在弹窗中说明错误。启用、停用、设为当前服务、删除使用相同的结果反馈规则。
- 通知初始为空，只由当次操作结果触发；浏览器刷新或打开旧 `notice/provider_name` 链接不产生通知。继续使用组件库的 notification、`native_dialog` 和确认气泡。
- 防止重复提交，完成后解除提交中状态。网络异常需显示结果未确认并允许用户重新检查状态，不将其误判为操作成功。

### 当前框架的适配边界

Topcoat 0.9.0 的原生表达式支持读取业务 `Result`，当前提交事件仍用最小 `raw!` 适配为 procedure 调用附加请求拒绝捕获，避免断网后一直处于提交中。没有独立业务 JavaScript 文件、手写 `fetch` 或 DOM 替换。筛选条件分别以字符串传入 shard。

原有 `/providers/save`、`/providers/action` 表单入口复用同一服务端处理函数，返回 JSON 结果；页面实际交互使用 procedure。两类入口均保留 Host、Origin、CSRF 与业务校验，不再返回通知重定向。

## 验证记录

- HTTP 集成回归直接请求页面绑定的原生 procedure，覆盖三种协议创建、编辑、版本冲突、启用/停用/激活/删除、Host/Origin/CSRF 防护与凭据不回显。
- 浏览器使用隔离 PostgreSQL schema 和临时 13200 端口，验证创建、编辑、启用、停用、激活后的名称通知及局部更新。网络记录仅出现 procedure 和 shard 的 Fetch 请求，没有文档导航。
- 带名称/协议筛选操作后 URL 和筛选保持；普通刷新、打开旧通知链接及再次刷新均没有成功通知。
- 服务端校验失败保留非敏感字段、清空 API Key；模拟断网显示结果未确认并恢复按钮。
- 完整验证通过：`cargo fmt --all -- --check`、`cargo check --workspace --offline`、`cargo test --workspace --offline`，共 33 项测试；临时测试服务和 schema 已清理。
