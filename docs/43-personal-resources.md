# 普通用户个人资源

用户确认：普通用户开放 Chat、Providers、Models、Model Routes、订阅节点、个人账户和独立虚拟 Keys 管理；采用个人资源隔离，不直接开放管理员已有数据。

## 设计与边界

- Providers、Model Routes、资源组、订阅节点记录 `owner_user_id`；模型继承 Provider 归属，Key 继承唯一资源组归属，Chat 与历史继承资源组上下文。
- 原有资源保持空归属，继续由平台管理员管理。管理员保留平台全局视图，普通用户仅访问自己的资源；用户管理、系统设置、节假日维护仍为管理员功能。
- 普通用户首次访问创建空的「个人资源」组；模型导入只进入个人模型目录，路由创建只进入个人路由目录。用户通过资源组详情主动添加模型/路由，允许同一账户内多组复用，禁止跨账户关联。
- `/ui/keys` 独立管理所选个人资源组的虚拟 Keys，复用资源组详情的创建、停用、撤销、授权与分页组件，明确显示当前组。所有写交互继续使用 Topcoat procedure、Signal 和响应式刷新。
- 登录与控制台首页统一进入 Chat。普通用户始终显示业务菜单，移除「仅开放个人账户」旧提示。
- Cookie 只表达组选择；服务器验证归属，不接受其作为授权依据。其他账户遗留的组 Cookie 回退到本人资源组；直接伪造资源/组 ID 的读写请求拒绝。
- 订阅代理仍通过既有登记流程接入。普通用户提供代理状态目录 `node.json` 中的 `node_id`/`node_key` 关联尚未启用且未归属账户的节点；已关联节点或已生成 Provider 的平台节点不能通过此入口转移。重连保持归属。
- 节点生成的 Provider 使用平台内部转接凭据，个人账户不能修改其连接配置或提交自定义预览目标，避免内部密钥被转发到其他地址；节点配置通过订阅节点页面管理。
- 禁用用户立即阻止该用户个人组 Key 的后续模型调用；现有无个人归属的 Key 保持原有行为。
- SQLite 与 PostgreSQL 均提供增量迁移；资源组名称按账户唯一，原有平台组名称继续唯一。

## 实施任务与验收

1. 数据归属与 Store 作用域：迁移、个人默认组、资源 CRUD/候选模型/分组关联检查。验证两个普通用户及原有平台数据相互隔离，同名个人资源可以共存。
2. 控制台权限与导航：请求注入个人 Store，开放业务页面、procedure、shard，保留管理员权限边界。验证菜单、页面响应、登录跳转及跨账户伪造请求。
3. 独立 Keys 页面与订阅关联：复用原生 Topcoat 组件；验证页内提交、表格更新、密钥一次展示及个人节点归属。
4. 回归：受影响测试、完整工作区测试、格式与 Clippy；浏览器验证普通用户实际操作。

组织及组织内共享尚未实现，不在此次个人资源改动中加入组织切换。

## 验证记录

- Store 42 项测试、资源组/Key 网关联调 6 项测试、用户认证 3 项测试通过。新增验证覆盖两个个人账户与原有平台资源隔离、跨账户伪造请求、过期组 Cookie 回退、Key 对模型列表与实际请求的授权，以及节点关联密钥校验和重连归属。
- 完整工作区回归 425 项通过、12 项忽略；随后追加的订阅 Provider 连接配置/预览目标保护测试通过。`cargo fmt --all -- --check`、新增节点关联组件的 Topcoat 格式检查及 `cargo clippy --workspace --all-targets -- -D warnings` 均通过。
- 隔离测试数据库中的浏览器验收通过：普通用户业务菜单、Chat 登录入口、独立 Keys 页面、Key 创建后表格自动刷新、停用及每页记录数选择；订阅节点关联对话框正常打开。
- PostgreSQL 迁移已提供；本机未配置 `LLMPROXY_TEST_DATABASE_URL`，未执行真实 PostgreSQL 数据库验收。
- 启动新版服务时自动执行数据库迁移。运行中的旧进程需重新构建并重启，再刷新页面。
