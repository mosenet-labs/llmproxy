## 1. 用户原始需求与确认

### 1.1 使用场景

> 我有多个设备分布在不同的地域都想使用一个chatgpt订阅账号，因此想共用api代理方案

用户是同一个订阅账号的使用者，希望通过统一代理，让自己的不同地域设备调用模型。本轮不是账号池、多个用户共享订阅或订阅转售服务需求。

### 1.2 会话和工具约束

> 1. 不想再codex进程本地保留会话
> 2. 不需要codex进程本地执行代理的工具调用

后续讨论确认：请求中声明的工具应交给客户端执行；代理不能因为使用 Codex 后端而在本地执行 Codex 内置工具。

已确认禁止 Codex 对话落盘，工具由最终客户端执行。目标行为是返回工具调用后结束本次 HTTP 请求并释放资源；下一次请求携带完整历史和工具结果。最终受控实现不创建 thread 或 turn。请求处理期间使用内存是必要的，但不保留跨 HTTP 请求、等待工具结果的 turn。登录凭据、节点身份和运行配置与对话历史分别管理。合成上游双轮工具往返已验证，真实账号验收另行记录。

### 1.3 两种后端与独立二进制

> 我希望实现两种方式
>
> 1. Sign in with ChatGPT 授权直接调用 Responses API
> 2. 本地调用 `codex app-server` 代理成 Responses API
>
> 这个需求与当前项目llmproxy关系为：
>
> 当前需求为一个独立的二进制，
>
> 1. 即可通过上面的两种方式代理成 Responses API 提供访问
> 2. 可以注册到远程的llmproxy上作为一个provider

两种后端都属于同一个独立二进制的可选能力，但每个进程只运行其中一种。二进制自身提供本地 Responses HTTP 服务，远程 llmproxy 不运行其本地 Codex 进程，也不接收其 ChatGPT OAuth 凭据。

“独立二进制”指独立构建和运行的可执行程序。本轮在当前 Rust workspace 中增加 `llmproxy-subscription-agent`，保持网关默认构建入口不变。Codex 模式仍需要可用的 Codex 可执行程序，不等于将 Codex 静态嵌入这个二进制。

### 1.4 采用反向连接

在“远程直接访问本地地址”和“本地主动连接远程”两个方案中，用户确认：

> 第二种方案，需要本地能够提供Responses API的http代理，又能注册到远程llmproxy，肯定是需要独立的二进制文件的

本地节点主动建立出站连接，远程 llmproxy 通过该通道派发请求。本地节点不需要具备可被远程访问的公网监听地址。本地 HTTP 服务和反向连接能力可以同时工作。

### 1.5 llmproxy 注册模块与服务准入

> 我觉得可以复用当前的代理功能，当前需求的注册上报在llmproxy上做为一个独立的模块，在llmproxy上显示健康状态，并可以配置是否可以加入到llmproxy中进行提供Responses API代理服务

已确认采用独立注册、健康和反向转接模块，尽量复用当前 Provider、模型映射、选路与 Responses 代理功能。注册成功不等于自动加入代理服务；是否加入由用户配置。

### 1.7 启动模式、认证和并发的最新确认

> 这个二进制启动的时候可以选择认证方式，默认直接复用本地codex的认证信息，可以指定chatGPT OAuth方式

> 那**后端选择方式**：启动时选一个，还是同一进程同时提供两个？同一进程支持两个后端，通过明确的模型映射选择，不自动切换。 我的建议是只支持一个

后端指模型调用路径，与并发对话数量是两个不同维度。确认的运行规则如下：

| 启动模式 | 认证来源 | 调用路径 |
| --- | --- | --- |
| `codex`，默认 | 本地已有 Codex 登录 | App Server → Responses 适配 |
| `chatgpt-oauth`，显式选择 | 本程序的 ChatGPT OAuth 授权 | 直接调用 Responses API |

启动时选择一种模式，运行期间不自动切换，也不通过请求中的模型映射切换后端。需要同时使用两种模式时，启动两个独立实例，分别配置本地监听和节点身份，并分别注册。

任一模式都要支持异步并发处理多个独立对话，同时服务本地 HTTP 请求和远程 llmproxy 请求。不同请求的历史、工具调用 ID、输出和取消相互隔离，两种入口共享容量限制。具体并发上限和 Codex 进程复用方式属于后续设计，不默认每个并发请求必须启动一个子进程。

### 1.8 完整 Responses 支持目标

关于 Responses 兼容范围，用户确认：

> 全部都支持，因为llmproxy的协议已经完全支持了

不人为将目标缩减为文本版或只支持流式。以完整 Responses 协议为目标，覆盖流式与非流式、消息历史、图片与文件输入、推理内容、客户端工具及结果、真实 usage 等已有协议能力，优先复用 llmproxy 的类型和转换逻辑。

协议支持与上游实际能力分别记录：上游支持的能力完整代理；上游限制的参数、输入或工具明确报错，不静默丢弃、不虚构能力、不自动切换后端。适配缺口属于待解决问题，不能通过缩减目标或无提示降级视为完成。

## 2. 总体架构

将“模型后端”和“请求接入方式”作为两个独立维度。启动时确定唯一后端，两种入口共用同一个请求处理服务，避免维护两套行为不同的代理逻辑。

```text
本地客户端 ── Responses HTTP ──→ 独立二进制
                                     │
远程 llmproxy ── 反向通道派发请求 ────┤
                                     ↓
                             共用请求处理服务
                                     ↓
                             启动时选定的唯一后端
                              · codex（默认）：App Server → Responses 适配
                              · chatgpt-oauth：直接调用 Responses API

反向通道由独立二进制主动建立，图中箭头表示请求派发方向。
```

独立二进制负责本地鉴权、后端认证、请求校验、模型调用、响应交付以及取消。远程 llmproxy 负责注册准入、在线连接、节点健康、是否参与代理、模型路由和反向请求转接。

用户目前没有要求增加 OpenAI Chat、Anthropic 或 ACP 接口，也没有要求在独立二进制中建立聊天历史数据库。Zed 的 Codex ACP 适配器只作为已讨论的候选，不纳入当前架构；它仍依赖 Codex，不能自动解决会话和工具执行约束。

## 3. 两种后端的能力边界

### 3.1 Sign in with ChatGPT 直接调用 Responses API

采用程序自己的官方授权流程，管理授权凭据与刷新。不能假定现有 Codex 登录缓存中的 token 可以直接替代本程序的 OAuth 授权。

这条后端接近原生 Responses 转发，但必须遵守订阅接入的当前限制。官方当前要求 HTTP 请求使用 `store:false`、`stream:true` 并携带所需上下文；不提供 HTTP 持久会话续接，也不支持全部常规 API 参数和托管工具。[官方接口限制](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)

对外支持 `stream:true` 和 `stream:false`。当上游仅支持流式时，非流式路径内部消费 SSE，依据真实终止事件返回完整 Response；不能将失败或未完成的流拼成成功响应。这属于代理适配能力，需要验证实现。

官方文档区分开源、本地应用与付费、远程托管应用，并提供自托管 VM 的凭据部署方式。本方案按个人自用节点设计；真实授权、模型访问和部署方式仍需验证，不把“可以登录”当作所有使用方式均获授权的证明。[接入范围](https://developers.openai.com/siwc/token-sharing-open-source) · [自托管 VM](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms)

### 3.2 Codex App Server 可以适配成 Responses API

结论是可以建立适配层。最终实现采用用户授权的受控 Codex 扩展：新增无会话 Responses RPC，复用 Codex 原生认证和账号区域路由，保留真实 HTTP 状态与 SSE 字节。

| Responses 行为 | 受控 App Server 适配 |
| --- | --- |
| 输入消息、媒体与历史 | 完整 request 经专用 RPC 交给原生 HTTP 客户端 |
| 流式输出、推理、工具、usage | 原生 SSE 字节转发，非流式按真实终态聚合 |
| 客户端工具往返 | 本次返回调用并结束；下一次提交完整历史及原始工具 ID |
| 错误及取消 | 保留上游错误；取消对应请求，不切换后端 |

原版 thread/turn 事件转换是讨论阶段候选，已被无会话 RPC 替代。上游不支持的参数明确返回错误，不丢字段或虚构能力。

本地桥接优先考虑 App Server 的 stdio RPC。它的 WebSocket 接口与独立二进制到 llmproxy 的反向通道是两套不同协议，不应混为一谈。[App Server 文档](https://learn.chatgpt.com/docs/app-server)

已确认 Codex 模式默认复用本地原生登录，优先让 Codex 自己加载和刷新凭据，不只读取一次 `auth.json`；凭据也可能存储在系统钥匙串中。[官方认证说明](https://learn.chatgpt.com/docs/auth)

两个后端的凭据由各自认证适配负责。Codex 模式如何在隔离运行配置的同时复用本地认证，仍需技术验证；不能强制要求该模式也取得本程序的 OAuth 授权。默认模式缺少有效认证时应明确失败，不自动进入另一模式。

## 4. 不保存 Codex 会话

每次 Responses 请求携带完整上下文，不依赖服务端持久会话续接。Codex 模式不创建 thread 或 turn，结束、取消、失败和返回工具调用后均释放请求资源。Response ID 和工具调用 ID 仍按协议正确返回，但不据此隐式保存会话；与服务端持久会话续接有关的参数不能静默忽略。

本机检查记录：2026-10-07，`codex-cli 0.155.0` 生成的 `ThreadStartParams` schema 包含 `ephemeral` 字段。这证明该版本存在协议参数，尚不能证明对话正文在所有本地存储路径中都不会落盘，也不能据此推断最早支持版本。

必须验证会话日志、数据库、运行日志、错误路径和异常退出后的残留。临时目录退出后删除不等于全过程不持久化；`store:false` 也不等于 Codex 本地会话不保存。

不持久化对话不妨碍保护和保存登录凭据、节点 ID、注册配置。用户没有要求删除远程 llmproxy 既有聊天历史功能，本需求不自动修改其历史策略。

## 5. 工具全部由客户端执行

### 5.1 客户端定义工具有官方委托机制

App Server 支持实验性的 `dynamicTools`。客户端声明工具后，Codex 可以通过 `item/tool/call` 请求客户端执行，并等待返回结果。[动态工具机制](https://learn.chatgpt.com/docs/app-server#dynamic-tool-calls-experimental)

但这里的“客户端”首先是连接 App Server 的 RPC 客户端，也就是我们的适配层。适配层还需要将调用转给最终 Responses 客户端，不能自己执行工具。

### 5.2 内置工具不会自动改成远程执行

shell、文件修改及其他内置工具与请求携带的动态工具分别处理。声明动态工具不等于替换全部内置工具；只读模式、关闭 shell、不给 MCP 或拒绝审批也不能单独证明所有工具不可执行。

需要建立并验证可靠的阻断边界。提示词不是执行边界；官方说明部分工具路径可能绕过通用 hooks，因此 hooks 也不能单独承担完整保证。[工具 hooks 覆盖范围](https://learn.chatgpt.com/docs/hooks#tool-coverage)

模型请求／输出过滤层是候选方案，需要验证传输覆盖、工具事件阻断、认证和版本兼容。如果它改用本程序的 OAuth 直连上游，必须明确这种依赖变化，不能把它作为保留原生 Codex 认证的等价方案。用户已确认允许受控扩展或补丁。最终补丁增加专用无会话 RPC，在进入 thread、turn、命令、文件或工具执行器之前拒绝其他 RPC；客户端工具仅作为请求与响应数据传递。

### 5.3 工具往返无需保留 turn

原版动态工具调用会等待 RPC 结果，不能仅转换事件名称。最终路径绕过 thread/turn：模型返回工具调用后结束当前请求，释放资源；客户端执行工具，再提交完整历史与 function_call_output。原始调用 ID 原样保留。代理与 Codex 均不等待下一轮工具结果，也不保存会话续接状态。

## 6. llmproxy 独立注册与转接模块

采用用户提出的模块方向，复用现有代理。当前阶段不要求修改 Provider 核心类型为新的反向 Provider 枚举。

```text
独立二进制
  ├─ 本地 Responses 服务
  └─ 出站连接、注册、健康上报
                 ↓
llmproxy 注册与转接模块
  ├─ 节点登记及在线连接管理
  ├─ 健康和能力展示
  ├─ 是否加入代理服务的配置
  └─ 受保护的 HTTP 转接入口
                 ↑
现有 Provider、模型映射、路由和 Responses 代理
```

转接模块提供真实的 HTTP 转接能力，将现有代理发来的请求派发给对应节点，再交回响应；不是将不可达的本地地址填入 Provider。由此复用模型名称改写、选路、协议代理及 SSE 处理。

转接入口是受保护的内部入口，不是可以任意访问节点 RPC、文件或工具的通用隧道。如何挂载到现有单端口服务、是否需要仅内部监听的端口，仍须验证后确定；尚未决定新增公共监听端口。

### 6.1 注册与参与服务分别管理

| 维度 | 含义 |
| --- | --- |
| 已注册 | 节点身份、名称、能力及模型信息已登记 |
| 在线／离线 | 反向连接是否有效 |
| 后端就绪／异常／未知 | 后端认证、进程或模型请求能力是否可用 |
| 允许加入代理服务 | 用户决定是否接入现有代理和路由 |

首次注册默认不加入代理服务。重新连接不覆盖用户的准入设置；断线保留登记和配置，但不继续向失效通道派发新请求。节点身份应稳定，名称作为展示信息，不能仅凭同名注册覆盖其他节点。

心跳在线不能证明模型可用。健康检测区分连接存活、本地后端状态与真实推理验证；不默认通过高频模型请求消耗订阅额度。模型目录也不能作为模型授权成功的证明。

用户确认按此建议执行：首次注册只登记；用户启用加入代理服务时，创建或关联普通 Provider，再通过现有模型配置加入路由。重连保留启用设置。关联的幂等规则、停用行为、模型目录更新和旧连接替换，需要在详细设计中明确；注册模块不绕过现有模型映射规则。

### 6.2 反向通道职责

反向协议至少覆盖注册认证、能力声明、请求 ID、响应状态、流式数据、并发限制、背压、取消、超时、重连和旧连接失效。

本地节点发起连接，并不改变请求的业务方向：远程 llmproxy 派发 Responses 请求，本地节点执行模型调用并回传结果。OAuth 和 Codex 登录凭据留在本地节点；本地 HTTP 访问凭据、远程注册凭据、在线连接凭据分别管理。

正在生成的请求遇到断线应明确失败，不自动重新提交推理请求。恢复连接与重放推理分别处理，避免重复消耗额度和重复输出。下游取消需要传播到本地后端，释放队列、RPC 等待和子进程资源。

远程请求与本地 HTTP 请求共享容量约束，不能分别绕过限制。队列和流式缓冲应有界，避免慢客户端导致内存持续增长。

### 6.3 反向通道传输选择

| 候选 | 优点 | 需要验证的成本 |
| --- | --- | --- |
| WebSocket | 双向派发、流式结果、取消和心跳可走同一连接 | Pingora 单端口 Upgrade 接入、连接生命周期和背压 |
| HTTP 长轮询＋流式上传 | 复用 HTTP 基础设施，通常更容易经过反向代理 | 派发、结果及取消需要关联，多条请求的超时和失效处理 |

本次实现选用 HTTP 长轮询派发和 NDJSON 流式上传，共用 Pingora 监听端口。它满足本地出站、NAT、流式结果及有界背压，不需要增加 WebSocket Upgrade 生命周期。注册返回短期租约，心跳续租并交付取消列表；节点断线取消当前远程请求并重连，不重放推理。公网连接采用 HTTPS，并分别验证注册密钥、稳定节点身份和短期租约。

## 7. 分层与设计模式

| 边界 | 职责与模式 |
| --- | --- |
| 后端接口 | 启动时用策略模式选择 OAuth 或 Codex，运行期间固定，不包含注册逻辑 |
| Codex 适配器 | 将 Responses 消息、工具和 SSE 与 RPC 转换，使用适配器模式 |
| 请求处理服务 | 接受两种入口的请求，共用校验、调用、错误和取消规则 |
| HTTP 与反向入口 | 使用端口与适配器分离接入协议，不复制后端执行流程 |
| 连接及请求状态 | 用状态机表达在线、派发、执行、流式返回、完成、失败及取消 |
| llmproxy 注册模块 | 管理节点与准入，向现有代理提供 HTTP 转接能力 |

只为已经存在的两种后端、两种入口建立必要边界，不引入通用插件框架、任意协议隧道或泛化任务调度平台。协议类型优先复用项目已有定义；能否复用既有 SSE 和 usage 适配器，在编码前按实际接口核实。

日志和指标记录后端类型、节点、请求关联 ID、状态、耗时和容量；不记录 OAuth 凭据、注册密钥、完整提示词、工具参数或完整响应正文。健康展示和错误信息不泄露这些内容。

## 8. 后端启用与完整服务验收条件

1. 默认模式正确复用本地 Codex 登录及凭据刷新，隔离配置不破坏认证；显式 OAuth 模式在目标账号及部署方式上完成授权、刷新和一次真实 Responses 请求。缺少认证、权限不足或模式失败不触发自动切换。
2. 受控 Codex 的无会话请求在正常、失败、取消和异常退出时不持久化对话正文。
3. 客户端工具经动态工具机制交付给最终客户端；所有不允许的内置工具在执行前被阻断。
4. 返回工具调用后正确结束 HTTP 请求并释放请求资源；在不创建 thread/turn 的方案下，完整工具历史能够恢复正确的工具往返，多工具调用及调用 ID 不串线。
5. 完整 Responses 目标覆盖流式、非流式、消息、图片、文件、推理、客户端工具、usage、错误和结束事件；逐项记录上游能力和适配结果，不支持能力有明确响应。
6. 反向通道可以接入现有代理，并保持注册与服务准入分离；连接在线与后端就绪分别展示。
7. 单后端模式下多个独立对话异步并发，本地和远程请求共用容量且上下文隔离；断线、慢客户端、取消、重连和旧连接替换不会泄漏资源或重放生成。

上述是技术验收条件，实施顺序见任务清单。当前未进行真实账号推理、真实工具双轮或跨地域 NAT 验收；本地回环 HTTP 的注册、反向转接、租约替换和控制台验证已通过。

## 9. 已确认的设计细化

### 9.1 启动时选择策略

启动配置只产生一个后端实例：默认 `codex`，显式选择 `chatgpt-oauth`。后端负责认证与模型调用，不负责注册；模型名称不能改变进程后端。两个后端真正共享的行为才进入最小接口，不先建立插件注册表或抽象工厂。

### 9.2 协议适配与接入分离

Responses 请求、响应和 SSE 类型复用 `llmproxy-core`。OAuth 后端保留原生载体，Codex 后端转换 RPC；不将所有协议先降为文本。上游必须流式时，对外非流式返回使用真实终止事件中的完整 Response，保留输出、推理、工具、usage、失败和未完成状态。

本地 HTTP 与反向入口只负责接入鉴权和传输，调用同一个请求服务；服务持有固定后端及共享容量，不复制两套推理流程。认证、队列和流式缓冲均有界，断开、取消和超时释放同一请求资源。

### 9.3 状态机与失败边界

请求状态为接收、执行、输出、完成／失败／取消、释放。工具调用交付后结束本次请求，下一次请求重新处理完整历史。请求 ID、取消对象和输出只属于当前请求。

连接状态为未连接、注册、在线、断线、重连。登记、连接状态、后端健康和用户准入是独立维度；恢复连接不重放推理，不覆盖启用配置。Provider 关联使用节点稳定身份，停用停止新请求派发，已经派发的请求按其生命周期处理。

### 9.4 实现约束

不引入通用工作流引擎、事件总线、插件框架和任意隧道。模块依赖方向为接入 → 请求服务 → 后端适配，远程注册独立组合。后端能力诊断区分接口存在、运行验证通过和未验证；有 `ephemeral` 字段不等于确认不落盘，有动态工具不等于确认禁止内置工具。

2026-10-07 的实验 schema 进一步确认存在 `thread/inject_items` 的原始 Responses 历史注入接口，以及 `thread/start.dynamicTools`。历史恢复有直接验证路径，不再仅考虑把历史拼成普通文本；具体语义和工具往返仍未验证。


## 10. 当前实现与未满足边界

独立二进制现在提供 `doctor`、`login`、`serve`。OAuth 使用官方动态公共客户端授权、受保护的原子凭据文件、串行刷新与轮换恢复记录；本地 HTTP 和远程请求共用同一容量信号量。流式输出只在真实上游正常结束后交付终态；非流式直接采用真实终态快照，保留 usage。请求正文和响应正文只进入有界内存缓冲，节点不保存对话。

注册元数据在 SQLite/PostgreSQL 保存，节点密钥加密；运行健康和在线租约只在内存保存。启用节点创建普通 Responses Provider，模型配置与选路继续使用现有功能。注册不自动创建模型或路由；重连不改服务准入。控制台入口为 `/ui/subscriptions`。

首批实现阶段 `codex` 启动明确拒绝；此段为历史分析，当前受控版本已接通，原版仍拒绝。检查到接口存在，但未证明所有内置工具在执行前均可阻断，也未完成正文落盘的所有路径验收。`approval_policy`、sandbox、`ephemeral` 和关闭 MCP 都不能单独作为这两项约束成立的证据。阅读当前公开源码发现内置工具仍通过核心工具源注册；源码分支与本机安装版本不同，该结果仅用于定位风险，不当作本机运行证明。A5/A6 保持未完成，需受控扩展或补丁的具体方案及原生认证、工具往返、落盘实测；用户已授权受控扩展／补丁，补丁及固定来源已放在 `crates/llmproxy-subscription-agent/codex`；不会修改机器已安装的 Codex。

OAuth 的协议载体保留能力不等于上游能力无限。当前官方订阅接口不支持音视频输入、上传 Files、部分常规参数和多数托管工具；本代理进一步禁止所有托管工具，只允许客户端 function/custom 工具及 namespace。客户端工具按官方要求使用 namespace 或 `additional_tools` 输入项；普通扁平工具声明是否可直接使用由上游校验，未进行真实账号验证。更多限制见[官方预览限制](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)。不能据 Core 支持某种载体就宣称两种后端均支持该能力。

运行方法、配置及仍需人工完成的验收记录在[任务清单](31-subscription-agent-tasks.md)。

## 受控扩展方案调整：无会话 Responses RPC

受控源码已通过编译及两项工具策略测试，但原始 RPC 通知缺少完整上游 Responses 终态快照，直接通过 turn 事件重建会丢失部分原生字段。A5/A6 因此改为在固定 Codex app-server 中增加专用 Responses RPC：通过 Codex 原生 ModelProvider／AuthManager 解析现有登录、刷新和账号区域路由，使用符合其网络策略且关闭请求日志的 HTTP 客户端，传递真实 HTTP 状态及 SSE 字节。此路径不创建 thread、不进入 turn 或工具执行器，不需要等待工具结果；下一次完整历史由客户端再次提交。

启动隔离仍保留：忽略用户／项目运行配置，关闭 SQLite 日志和遥测重载，原生认证使用 Codex 的 Auto 存储读取机制以兼容 keyring 及 auth.json，不将凭据传给代理。专用 RPC 仅在受控进程模式启用，原版或未确认版本拒绝推理。禁止 hosted 工具，function/custom/namespace 声明及调用结果作为数据传递；API 不支持的字段返回真实错误，不静默丢弃。进程复用同一认证管理器，代理对并发请求做有界关联、取消和结束处理。旧 thread/start 工具策略试验不作为最终代理路径。

这仍属于 codex 后端，使用 Codex app-server 和原生认证，没有改为本程序 OAuth。需验证区域路由、无自动请求重放、并行流及断开取消、正常／错误／取消／崩溃的正文不落盘，完成后才能启用。

## 节点展示名称与模型选择（2026-10-08）

- agent 的 `--name` 可选；首次注册未提供名称时使用 `node-<6 位短 hash>`，短 hash 取自随机生成并持久化的节点身份，不包含汉字。
- 服务端可以编辑名称；重连更新能力声明但不覆盖名称。名称编辑与关联 Provider 名称更新在同一事务中完成。Provider 名称冲突时附加节点短 hash。
- agent 的 `--models MODEL[,MODEL]` 声明多个可代理模型。订阅 Provider 的模型查询路径复用现有内部 `/models` 接口，返回注册声明中的模型列表，与 agent 本地 `/v1/models` 一致；无须公网直连 agent。
- 首次允许加入后跳转模型选择页，按需勾选导入；已关联节点可补充导入。服务端重新查询列表验证选择，去重并跳过已导入的映射，只创建 Responses 模型映射。导入不自动配置路由。
- 既有节点在保存名称或重新设置准入时更新 Provider 展示名称；不会因为重连自动修改已有模型别名。
