# 历史会话与逐轮模型用量需求分析

## 1. 文档状态与目标

本文为历史会话与用量统计的需求基线。表结构、接口、实施任务和当前验收结果见 [架构与实现文档](29-conversation-history-implementation.md)。

目标：保存 Chat 页面的历史会话，在刷新页面或服务重启后恢复内容并继续聊天；同一会话允许混用模型和协议，每轮独立记录实际模型及 token 消耗，并提供逐轮与会话汇总展示。

## 2. 术语与范围

| 术语 | 定义 |
| --- | --- |
| 会话 | 一段连续聊天，包含标题、当前选择及多轮历史 |
| 轮次 | 一次用户提交及其对应回复、错误或停止结果；每轮有独立 ID 和顺序 |
| 请求 | 本轮发给 Gateway 的一次 HTTP 请求，通过请求 ID 关联实际路由和用量 |
| 模型选择 | 用户选择的模型映射或路由，以及客户端使用的模型别名 |
| 实际模型 | Gateway 路由确定的 Provider 和上游模型；与响应报告的模型名称分别记录 |
| 用量快照 | Provider 已报告、经来源协议解码后归一化的 IR Usage |

本期对象为当前 Console Chat 页面创建的会话，覆盖 Chat、Responses、Messages、Gemini，包含流式与非流式。外部 LLM Agent 的全部请求归档、费用核算、会话分支和工具自动执行留待独立需求确定。

## 3. 当前基础与缺口

| 部分 | 当前实现 | 本次需要补充 |
| --- | --- | --- |
| 会话生命周期 | Console 使用内存 `ChatSessions`；页面初始化创建会话；闲置会话按一小时回收 | 数据库记录、历史列表与加载、刷新和重启恢复 |
| 对话上下文 | `chat_stream::history` 保存有序 Core IR，支持同会话切换模型和协议 | 持久化有序 IR，加载后恢复发送上下文 |
| 每轮模型 | 内存保存选择、别名、响应报告模型和思考设置 | 保存当时快照，补充 Gateway 实际 Provider、上游模型及 Provider 协议 |
| 用量 | `ChatReply` 已有类型化 Usage；会话将其转换为展示字符串 | 保存完整 Usage，统一统计数据源，提供可查询指标 |
| Gateway 统计 | 跨协议转换和同协议流式观察已有来源 Usage 采集及可观测性记录 | 将采集结果与持久化轮次关联，覆盖全部转发路径 |
| 工具续传 | 已有独立数据库记录及有效期 | 明确历史恢复与续传状态有效期之间的关系 |

当前浏览器页面作用域 `scope` 是临时值，需要补充稳定的会话归属策略，才能恢复历史。

## 4. 功能需求

### 4.1 会话保存与恢复

1. 每个会话使用稳定 ID，保存标题、创建时间、更新时间和当前模型／协议／思考偏好。
2. 每次用户提交生成独立轮次，按顺序保存输入、回复和执行状态。
3. 刷新页面和重启服务后，能够查询旧会话、加载详情，并在原会话继续聊天。
4. 新会话获得新 ID；切换模型或协议保持原会话 ID 和旧轮内容。
5. 标题、历史内容与实际统计来自数据库；内存只承担活跃生成和页面增量更新。
6. 新建记录后再次保存或重复完成回调，应更新同一记录，避免重复轮次和重复统计。

### 4.2 逐轮模型记录

每轮固定保存当时选择与实际调用结果，至少包含以下信息：

| 信息 | 内容与来源 |
| --- | --- |
| 用户选择 | 模型映射 ID 或路由 ID、客户端模型别名；由 Console 在提交时固定 |
| 客户端协议 | 本轮入口协议；由 Console 与 Gateway 请求确认 |
| 实际 Provider | Provider ID 与名称快照；由 Gateway 实际路由结果提供 |
| 实际模型 | 模型映射 ID、上游模型标识；由 Gateway 实际路由结果提供 |
| Provider 协议 | 本次实际使用的上游协议；由 Gateway 提供 |
| 响应模型 | Provider 响应报告的模型名称；未报告时保持缺失 |
| 思考设置 | 本轮默认／开启／关闭选择及实际应用设置；分别保留用户意图和生效结果 |

历史展示以实际调用快照为准，并允许查看用户选择。模型或 Provider 配置修改、禁用或删除后，已保存的名称和用量仍可展示。响应报告模型不能替代路由模型快照，也不能覆盖会话下一轮的选择。

在请求尚未选中 Provider 就失败的情况下，实际 Provider 和上游模型保持缺失，不从别名推测。

### 4.3 历史内容

- 以类型化 IR 保存有序输入和回复，保留文本、工具调用与结果、多模态引用及所需来源信息；通过序列化形式存入数据库，读回后恢复类型。
- 可见思考／摘要、音频转录、转换提示和错误信息作为展示数据保存；构造下一轮请求继续遵守当前 IR 历史兼容规则。
- 展示字符串、Markdown、模型标签和用量文案不作为重建上下文的数据源。
- 成功正常结束的有效回复可进入后续上下文；达到输出上限时按现有协议结束规则处理。
- 失败、用户停止或传输截断的记录仍出现在历史中；部分回复与错误说明分别保存，避免错误文案替代已生成内容并被发送给模型。
- 签名、私有文件和协议专属内容继续按原模型／作用域及转换规则处理，不能因持久化而跨模型自动复用。

媒体二进制的存储位置和保留期限需要另行确定；保存 URI 或文件 ID 不能保证对应资源长期有效。历史中的工具续传引用也需检查现有续传状态是否仍有效，恢复历史不自动延长其有效期。

## 5. token 与缓存统计

### 5.1 每轮指标

复用 `ir::usage::Usage` 与 `ir::cache::CacheUsage`，保存完整结构，并为常用查询指标提供可查询的数据库字段。结构与查询字段由同一份快照在同一次保存中生成。

| 指标 | IR 字段 | 统计口径 |
| --- | --- | --- |
| 输入总量 | `input_tokens` | 归一化后的本次输入总量，含发送的历史上下文及缓存输入 |
| 输出总量 | `output_tokens` | 归一化后的本次输出总量，包含按协议规则计入其中的推理用量 |
| 总量 | `total_tokens` | 本次请求总用量；保留来源 IR 的归一化结果 |
| 未缓存输入 | `input_details.uncached_tokens` | Provider 报告或按已知计数可靠推导的普通输入部分 |
| 缓存读取 | `cache.read_input_tokens` | 本次从提示缓存读取的输入 token |
| 缓存写入 | `cache.write_input_tokens` | 本次写入提示缓存的输入 token |
| 短时缓存写入 | `cache.write_short_input_tokens` | Provider 报告的短时缓存写入细分 |
| 长时缓存写入 | `cache.write_long_input_tokens` | Provider 报告的长时缓存写入细分 |
| 推理用量 | `output_details.reasoning_tokens` | Provider 报告的推理 token |
| 模态及其他细分 | Usage 中已有的输入、输出和缓存明细 | 保留完整结构，按已支持的 IR 映射读取 |

缓存命中指 Provider 提示缓存读取，不能根据 HTTP 缓存、客户端历史重复文本或思考摘要长度推算。

### 5.2 统计规则

1. 用量来源为实际 Provider 响应解码后的来源 IR，采集早于客户端协议编码。目标协议无法表达的缓存写入、TTL 或模态细分仍应保留在记录中。
2. 输入量按本次实际请求统计，包含重复发送的历史上下文；整个会话累计量是各次请求的消耗之和，不能对重复历史 token 去重。
3. 缓存读取／写入属于输入细分，推理属于相应输出细分；页面和汇总不能再次把这些细分加到总量上。
4. 未报告的计数保存为 `NULL`；明确报告零保存为 `0`。缺失字段不能由页面补零或用本地 tokenizer 冒充实际用量。
5. 流式数据交给现有 IR 用量汇总器处理；累计快照以更新方式保存，不能将各 SSE 帧中的累计值相加。
6. 每个请求 ID 只形成一份统计结果；保存重试不产生新增消耗记录。若实际发生多次 Provider 尝试，须分别记录尝试和用量，不能覆盖前一次真实消耗；具体请求／尝试关联在接口设计阶段确定。
7. 执行状态与用量完整程度分别保存。失败或停止可能已消耗 token，保留已报告数据；请求成功也可能没有报告用量。
8. 用量完整程度至少区分未报告、部分快照和已取得协议规定的最终用量。最终判定依据 Provider 报告及协议生命周期，不能只根据是否收到文字或 HTTP 200 判定。

### 5.3 缓存命中率与会话汇总

- 单轮缓存命中率：`缓存读取 token / 输入总 token × 100%`；两项必须有效且输入大于零。
- 会话及模型分组命中率：仅对两项都已知且统计口径可比较的轮次，计算 `缓存读取合计 / 对应输入合计`；不能平均各轮百分比，也不能把未知缓存读取当作零加入分母。
- 输入、输出、总量和缓存读写分别汇总已报告值；统计不全时展示已报告合计及缺失／部分记录数量。
- 失败、停止和中断轮次中已知的实际消耗仍计入已报告汇总，标明其状态和完整程度。
- 按实际 Provider＋上游模型分组；相同模型名在不同 Provider 下分别统计，多个客户端别名指向同一实际模型时可合并。

## 6. 页面需求

### 6.1 历史列表与恢复

建议历史列表按最近更新时间分页，展示标题和更新时间。进入旧会话加载已保存轮次，恢复当前选择及偏好。

如果原模型／路由已不可用，旧历史仍可查看；继续聊天时提示选择有效目标。历史显示不因配置删除而失败。

### 6.2 每轮展示

每条模型回复下展示：

- 实际 Provider、模型、协议和本轮思考选择；需要时展开用户选择及响应报告模型。
- 输入、输出、总量、缓存读取／写入、推理 token；未报告字段显示“未报告”。
- 有效数据下的缓存命中率，以及执行状态、用量是否完整。
- 已有思考摘要和转换提示。

生成时继续逐帧更新内容；已报告用量标为暂时快照，结束后从权威记录展示最终结果。刷新后展示应与结束时保存的数据一致。

### 6.3 会话汇总

会话区域提供：

1. 整个会话的调用次数、已报告输入／输出／总量、缓存读取／写入和缓存命中率。
2. 按实际 Provider＋模型分组的同类统计。
3. 统计缺失或仅有部分数据的说明，防止把已报告合计显示成完整实际消耗。

模型配置或会话当前选择的变化不改变旧轮统计和分组依据。

## 7. 建议的数据组织

以下为逻辑数据划分，具体表结构、索引及公开类型在后续设计中确定。

| 记录 | 建议保存内容 |
| --- | --- |
| 会话 | 稳定 ID、归属标识、标题、当前模型／路由选择、当前协议、思考偏好、创建和更新时间 |
| 轮次 | ID、会话 ID、顺序、输入与回复 IR、展示内容、请求关联、选择快照、实际调用快照、Usage、用量完整程度、状态、错误、开始和结束时间 |

建议首版以会话和轮次为主要记录。需要保存多次实际 Provider 尝试时，再按实际转发机制明确请求统计记录与轮次的关联，避免把某次尝试的用量当成整轮总量。

会话 ID、轮次 ID、请求 ID 分工明确，不能使用 Provider 响应 ID 替代本地关联标识。轮次 ID 和会话内顺序应具备唯一约束；输入保存、终态保存与会话更新时间更新保持事务一致。

历史数据中的模型／Provider ID 用于关联，名称和协议快照用于展示。配置记录的删除不能级联删除对话历史。

## 8. 保存、恢复与模块职责

建议流程：

```text
提交输入
  → 固定本轮选择与设置
  → 保存用户输入和生成中轮次
  → 请求 Gateway，并关联本地请求 ID
  → Gateway 记录实际路由结果
  → Provider 响应解码为来源 IR
  → 采集 Usage，同时继续向页面交付内容
  → 完成／失败／停止时保存终态、回复及已报告用量
  → 更新会话时间与汇总展示
```

先保存输入再请求 Provider；保存失败时给出明确反馈。内容记录与用量记录通过稳定 ID 关联，生成结束的回调不得把先前已经保存的来源 Usage 覆盖为客户端协议中的较少字段。

首版建议流式内容在内存中增量更新，结束时保存最终快照。需要意外退出前的部分内容恢复时，再加入节流检查点。服务重启后，没有活跃生成任务的遗留 `generating` 记录转换为 `interrupted`；不自动重发请求，避免产生额外消耗。

持久化失败应显示保存状态，与 Provider 生成状态分别处理，不能给出“已保存”的错误承诺。具体重试和一致性机制在接口设计阶段确定。数据库写入不能按每个 token 或 SSE 帧阻塞转发；同协议透传继续保持原始流式字节与增量交付。

| 模块 | 职责 |
| --- | --- |
| Core IR 与 ProtocolCodec | 共用内容和 Usage 类型、四协议归一化、历史兼容转换 |
| Gateway | 实际 Provider／模型快照、来源用量采集、请求关联与完成状态 |
| Store | 会话与轮次持久化、事务、分页查询及统计查询，支持现有 SQLite／PostgreSQL |
| Console `chat_sessions` | 活跃会话协调、历史恢复、生成状态与持久化调用 |
| Console `chat_stream::history` | 有序 IR 上下文整理，恢复后构造目标协议请求 |
| Chat 页面 | 历史选择、逐轮模型和用量、会话及模型分组汇总 |

历史内容与签名的存储处理沿用项目现有凭据／私有状态保护边界；公开展示数据不暴露签名，API Key 和认证请求头不属于历史记录内容。

## 9. 验收标准

| 场景 | 验收结果 |
| --- | --- |
| 刷新与重启恢复 | 内容、顺序、思考摘要、模型快照、已报告用量和状态保持一致；旧会话可继续聊天 |
| 同会话切换模型 | 按 A→B→A 完成多轮，旧轮模型不变，汇总按实际 Provider＋模型正确分组 |
| 四协议及响应模式 | 四协议同协议与跨协议请求在流式／非流式下均可记录；继续聊天使用恢复的 IR |
| 实际路由与响应模型 | 用户选择、路由结果和响应模型各自保存；客户端响应中的别名重写不影响真实模型统计 |
| 配置变化 | 修改、禁用或删除模型／Provider 后仍可展示历史快照及原统计 |
| 跨协议用量细分 | 来源提供的缓存写入、TTL、推理或模态细分在目标协议无法表达时仍完整记录 |
| 缺失与明确零值 | 未报告显示“未报告”，明确零显示 `0`；统计不会把缺失当作零 |
| 流式累计快照 | 多次重复或递增 usage 事件不重复累加；内容保持增量交付 |
| 幂等保存 | 相同轮次／请求重复保存、重复完成回调不增加轮次数和消耗 |
| 失败、停止及中断 | 执行状态和用量完整程度正确；已报告消耗保留；不完整回复与错误文案不污染上下文 |
| 会话与模型汇总 | 已报告合计、缺失覆盖情况和加权缓存命中率正确，无细分重复计数 |
| 数据库兼容 | SQLite 与 PostgreSQL 的迁移、读写、关联与统计口径一致 |
| 历史资源恢复 | 工具、媒体、签名按现有兼容规则恢复；过期／不可用资源给出明确反馈 |

## 10. 待确认事项

1. **会话归属**：工作区共享历史、稳定浏览器身份或登录用户。当前临时 `scope` 无法承担刷新后的归属。
2. **保留和删除**：会话是否长期保留、是否提供用户删除入口，以及清理规则。
3. **中断内容**：首版只在轮次结束时保存内容，还是需要生成期间的节流检查点。
4. **资源保存**：音频、图片、文件等内容的存储位置与保留期限；工具续传状态到期后的恢复行为。

本轮采用的默认选择已在 [架构与实现文档](29-conversation-history-implementation.md) 落地：工作区共享、长期保留并手动删除、结束时保存正文、沿用现有媒体与工具有效期。金额统计需结合价格版本及计费口径另行设计，本版只记录和展示 token 用量。
